How I set up my AI workflow.

How I set up Claude for UX work so it builds for my product team, stakeholders, developers and users, not for an average product. Five steps you can copy, starting with the content.

01 / Problem statement

Generic is the default

Ask Claude for a screen or a line of copy for a trading app and it fills every gap with the average of what it has seen: stock buttons, stock wording, stock flows. Read the result without the brand name. If it still sounds right for any company in the category, that is the tell.

I want designs that fit my product team, my stakeholders, my developers and what users told us. The ingredient that decides that is content. Claude can only use what it has been given, and it forgets between sessions. Rules said once drift back, and a new session starts blank. The way out was to write the content and the guidelines down, in places it reads on its own.

02 / Setup

What Claude is connected to

Two zones. The brain is everything Claude can draw on. The workboard is where it does the work.

03 / Process

Five steps to copy

5 steps, in the order I would do them. Each one works without the next.

Step 1. Bring your real content in. This is what keeps the result from being generic. Gather four things: user feedback or research findings, what your stakeholders insist on, your developers' real limits, and your design system guidelines. Save them as files in the project, or connect the app where they live. Mine are 3 connectors: Figma, Atlassian (Jira and Confluence) and Mobbin, through MCP. I also give it a browser it can drive so it can look at the screen it built and not only read the code. Add the next app once the first has earned its place. Learning ten tools at once ships nothing.

Step 2. Write the guidelines down once. Put them in the file Claude reads at the start of every session (CLAUDE.md in Claude Code, project instructions in Claude on the web). Start with three or four lines, then add one each time it breaks a rule. Mine began with this, from my workshop:

No em dashes, en dashes or arrows. Use commas, full stops or semicolons.
Tone: grounded, direct, conversational. Not cheerful or customer-service-like.
If a prompt is too vague or missing detail, say so and ask. Do not guess or invent.

Step 3. Give every project the same folders. I use 4: source for what I was sent, such as feedback and requirements, work for my thinking, output for what leaves the project, tools for scripts. Say the layout once in the guidelines file. Your content then has a fixed home, and Claude knows where a file goes.

Step 4. Save a lesson the first time something breaks. One fact, why it matters and what to do next time. I merge pull requests while Claude works. It once force-pushed without checking the remote, and two of my merges were erased. Now there is a note: fetch and compare before any force-push.

Step 5. Add 1 check, in a separate pass. A better prompt is not a check, and "sounds plausible" is not a source of truth. Check the result against your content. In a content project, the first draft left out a required legal notice, and a dedicated review pass caught it. For this site, a script checks forbidden characters, image formats, text size and sideways scrolling. Keep each check narrow: "check every shelf for dust" finds more than "tidy the room".

04 / Reflection

What I'd change, and the rule I took

I have not measured whether the setup cuts the drift. What I have is the workshop example and the fact that my guidelines now outlast a session. A fair test would run one task with and without the guidelines file and count the broken rules.

The rule I took: if I have said it twice, it goes in a file.
